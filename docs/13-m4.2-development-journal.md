# AI Bridge — M4.2 Development Journal & Custom Review Rounds

## 1. Goal

Two things a person running a multi-hour Claude ⇄ Codex loop keeps asking for that M4/M4.1
didn't cover:

1. **A plain-English record of what happened**, round by round, without opening raw JSON
   or piecing together `.ai-bridge/sessions/<id>/NNN-*` files by hand.
2. **Control over how many review rounds a run is allowed to take** — not just the fixed
   `maxIterations` from `config.json`, but a per-run choice made when starting.

Both had to be built **without** touching the safety/recovery/permission model M3–M4.1
already proved: same one-run lock, same crash recovery, same IPC allowlist, same "never
fabricate a session id/token count/result" rule. The journal is generated *from* the
artifacts Core already writes and verifies — it is a second read of already-trusted data,
never a second source of truth.

## 2. Existing architecture reused

Nothing new was introduced at the orchestration layer. M4.2 adds:

- `src/core/journal/journal-types.ts` — the `JournalEntryKind` enum and its validity
  check, in a file with **zero imports** (see §11 — this exists purely so the sandboxed
  renderer's esbuild bundle can share it without pulling in Node builtins).
- `src/core/journal/journal.ts` — pure functions that read `SessionArtifacts`/
  `SessionSummary` (both already produced by `core/session-history/session-history.ts`)
  and render Markdown, plus the small amount of I/O needed to write/read those Markdown
  files inside the *existing* `.ai-bridge/sessions/<id>/` directory.
- Two new `BridgeEngine` methods (`getJournal`, `getJournalEntry`) that call the above,
  following exactly the pattern `getSessionArtifacts`/`getExecutionOutput` already used.
- Two new IPC channels (`bridge:getJournal`, `bridge:getJournalEntry`), validated the same
  way every other channel is, exposed through the same frozen `window.aiBridge`.
- One new React component (`JournalPanel.tsx`) and one new tab (`JOURNAL`) in the existing
  `ArtifactViewer`.

`Orchestrator`, `SessionManager`, the state machine, the recovery decision table, the lock,
and the IPC router are all **unchanged**.

## 3. Iteration semantics: `maxIterations` as a per-run choice

`maxIterations` was already a `BridgeStartOptions` field and already persisted into
`current-session.json` since M4 (so resume already preserved it). What M4.2 adds is a hard,
explicit ceiling and a UI for picking it:

- `MAX_RUN_ITERATIONS = 100` (`core/config/config.ts`) and the matching
  `MAX_ITERATIONS_LIMIT = 100` (`desktop/shared/ipc-contract.ts`) are the one safety cap,
  checked in two places: `BridgeEngine.start()` (CLI + desktop) and the IPC validator
  (desktop only, defense in depth — a compromised renderer still can't ask Main for 500).
- `start()` returns a new outcome kind, `INVALID_OPTIONS`, when `maxIterations` isn't an
  integer in `[1, 100]` — **before** preflight, **before** acquiring the lock. No run is
  ever silently clamped to the cap; an out-of-range request is refused outright.
- The loop itself was already correct (`for (iteration = startIteration; iteration <=
  maxIterations; …)`, `STOPPED_MAX_ITERATIONS` when the loop exhausts without a DONE/
  NEED_HUMAN decision) — M4.2 only had to make sure the *cap itself* was configurable,
  validated, and visible, not rewrite the loop.
- Desktop: `StartRunDialog` shows a **preset select** — 1, 2, 3, 5, 10, 20, 30, 50, or
  "Custom…" (revealing a plain number input, 1–100). The label reads "Maximum review
  rounds" with the hint *"Maximum rounds — run stops earlier if reviewer returns DONE."*
  There is no way to type a number into the UI that submits above 100 — the field itself
  won't validate, and `bridge:start`'s IPC validator would refuse it even if it somehow did.

## 4. Journal structure on disk

Reuses the *existing* `.ai-bridge/sessions/<runId>/` directory and the *existing* `NNN-*`
artifact names — no new directory, no renamed files:

| File | Kind | Written by |
|---|---|---|
| `NNN-claude-prompt.md` | exact prompt sent to Claude | Orchestrator (M2) |
| `NNN-chatgpt-review.md` | Codex's **raw** response | Orchestrator (M2, legacy name) |
| `NNN-extracted-prompt.md` | exact next prompt (the `<PROMPT>` Codex returned) | Orchestrator (M2) |
| `NNN-claude-report.md` | **new**: verified metadata + Claude's report, verbatim | `journal.ts` |
| `NNN-review.md` | **new**: Codex's narrative review, verbatim + parsed decision + next-prompt pointer | `journal.ts` |
| `session.md` | **new**: whole-session index (rounds table, artifacts, ids, token usage) | `journal.ts` |
| `final-report.md` | **new**: whole-session report (only once the run reaches a final status) | `journal.ts` |

`NNN-claude-report.md` and `NNN-review.md` are **generated**, not copied — they add
metadata (session ids with their evidence level, exit codes, token usage) around the
verbatim text, so a reader never has to cross-reference a second file to know whether a
session id was actually confirmed by the CLI. All generation is **idempotent**: every write
goes through `writeIfChanged` (temp file + rename, and skipped entirely if the content is
byte-identical), so a rebuild after resume/crash never creates a duplicate round or a
torn file a concurrent reader could see half-written.

## 5. Claude report contract

`Claude Execution Report` (`renderClaudeReport`) is built from two already-trusted sources:

- The **M4.1 execution record** (`NNN-claude-execution.json`) — session id + its evidence
  level (`CONFIRMED_BY_CLI` / `REQUESTED_NOT_CONFIRMED`), continuity verdict on resume,
  exit code, start/end/duration, prompt SHA-256/bytes, and now **token usage** (§8).
- The **validated report** itself (`.ai-bridge/reports/NNN-report.md`, or recovered from
  what was sent to Codex if overwritten — exactly session-history's existing
  `ReportArtifact` logic), included **verbatim** under "Report (verbatim)", with a note on
  whether its SHA-256 still matches the integrity record.

Nothing here is written by asking Claude (or any model) to summarize itself — the
"Report (verbatim)" section *is* Claude's own file, unmodified.

## 6. ChatGPT review contract

`ChatGPT Review` (`renderReview`) does the same for Codex's side:

- Session metadata (Claude session + Codex thread, both with evidence), Codex's own token
  usage.
- **`## Review (Codex, verbatim)`** — the text Codex wrote *outside* the
  `<AI_BRIDGE_RESPONSE>` block (`codexNarrative()`), i.e. exactly the human-readable
  Markdown review the M4.2 reviewer-input contract now asks Codex to write first (§9).
  If Codex returned only the structured block with no narrative, this section says so
  plainly rather than inventing one.
- **`## Decision`** — the `STATUS` the *response parser* extracted, never re-derived from
  the narrative text. The parser stays authoritative for control flow; the journal is a
  read-only view onto its decision, not a second parser.
- **`## Next Prompt`** — the exact next prompt (`NNN-extracted-prompt.md`, SHA-256 + bytes),
  with a note on whether it was actually sent to Claude (`CONTINUE`) or the run ended
  before it could be (`DONE`/`NEED_HUMAN`).

## 7. Final report contract

`renderFinalReport` is written **once**, when `summary.status` reaches one of
`DONE | NEED_HUMAN | ERROR | STOPPED | STOPPED_MAX_ITERATIONS` — never mid-run, and never
rewritten with different content once the run is over (idempotent like everything else).
Sections, in order: Task, Session, Executive Summary, Development Timeline (per iteration:
Claude Summary / ChatGPT Review / Result), Major Development Phases (Codex's own
`## Development Phase` headings, collected — omitted per round if Codex didn't write one),
Files Changed (Created/Modified/Deleted, as Claude reported them), Tests, Important
Decisions, Problems Encountered, Problems Resolved (always **UNKNOWN** — AI Bridge does not
infer resolution; a reader is told explicitly to compare rounds themselves), Remaining
Work, Known Risks, Architecture Summary (always "not generated" — same reason), Interaction
Timeline (the verdict chain, plus a Mermaid flowchart in a fenced code block — rendered as
text, per §10; Mermaid execution was never in scope), Final Result. Every section marked
"as reported by Claude" / "as reviewed by Codex" is a direct quote, labelled as such.

## 8. Token usage

Real, CLI-reported numbers only — parsed once, in `core/execution/execution-record.ts`,
and reused everywhere (journal, ExecutionPanel):

- **Claude**: the `result` stream-json event's `usage` object — `input_tokens`,
  `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`. Total =
  their sum (labelled with the exact formula in the journal, so a reader can verify it).
- **Codex**: the last `turn.completed` event's `usage` object — `input_tokens`,
  `cached_input_tokens` (a subset of input), `cache_write_input_tokens`, `output_tokens`,
  `reasoning_output_tokens` (a subset of output). Total = input + output.
- If a CLI's stdout has no parseable usage object, `ExecutionRecord.usage` is `null` and
  the journal prints **`UNKNOWN (the CLI reported no usable token usage for this call)`**
  — never a guess, never "0". Verified with the real CLIs (§13): both reported real usage
  in the actual run.
- This is **per-call usage**, explicitly labelled as such — never presented as, or confused
  with, account-level quota.

## 9. Reviewer contract change

`buildReviewerInput` (`prompts/templates.ts`) now asks Codex to write a Markdown review
**first**, outside any XML-like tags — headings `## Summary`, `## What Was Done
Correctly`, `## Problems Found`, `## Required Changes`, `## Development Phase` (only when
clearly established), `## Next Objective` — and only *then* the existing
`<AI_BRIDGE_RESPONSE>` structured block the parser reads. The parser's contract is
unchanged: it still requires the block, still validates `STATUS`/`PROMPT` the same way,
still allows narrative text before/after the block (this was already true — `journal.ts`
simply reads that pre-existing allowance to get the narrative for `codexNarrative()`).

`buildReportContract` gained a few new recommended sections (`FILES CREATED`, `FILES
MODIFIED`, `FILES DELETED`, `VALIDATION`, `DECISIONS`, `REMAINING WORK`, `SUMMARY`) and an
explicit instruction that this is an unattended automated run: Claude must not ask
questions and must write the report file with a tool call, not just answer in chat (a real
M4.1 failure mode — a report "missing" because Claude answered conversationally instead of
writing the file — is now called out by name in the prompt).

## 10. Markdown viewer

`lib/Markdown.tsx` is a small hand-rolled renderer (no `dangerouslySetInnerHTML`, ever) —
M4.1 already had headings, paragraphs, lists, tables, fenced code, inline code, bold/
italic. M4.2 added:

- **Blockquotes** (`>` lines) and **horizontal rules** (`---`/`***`/`___` alone on a line).
- **Links** `[text](url)` — rendered as real `<a>` elements (so they look and copy like
  links), but `href="#"` and a click handler that unconditionally calls
  `preventDefault()`. Reports/reviews are AI-written and therefore untrusted content by
  policy (M4's stance is unchanged); nothing in one can navigate this app anywhere.
- Fenced code with an unrecognized info string (e.g. ` ```mermaid `) still renders as a
  plain code block — Mermaid is explicitly **not** executed/rendered as a diagram; the
  spec allows this ("Mermaid optional") and rendering arbitrary Mermaid text as an SVG
  would be a bigger trust boundary than this milestone needed to cross.

The same component now also renders every journal entry (`LazyJournalEntry`), with the
same Rendered/Raw toggle already used for the REPORT tab.

## 11. Desktop wiring

- **IPC contract** (`desktop/shared/ipc-contract.ts`): `bridge:getJournal` (`{runId}` →
  `JournalIndex`) and `bridge:getJournalEntry` (`{runId, kind, iteration?}` →
  `JournalEntry`). Validated like every channel: `runId` must match
  `YYYY-MM-DD_NNN`, `kind` must be one of the seven `JournalEntryKind` values, `iteration`
  (when present) an integer 1–999.
  A subtlety worth naming: `JOURNAL_ENTRY_KINDS`/`isJournalEntryKind` had to be pulled out
  of `journal.ts` into a separate zero-import file (`journal-types.ts`), because
  `ipc-contract.ts` is bundled into the **renderer** (browser platform, no Node builtins
  available) and `journal.ts` imports `node:fs/promises`/`node:path` for its actual I/O.
  Everything else the renderer needs from `journal.ts` (`JournalEntry`, `JournalIndex`,
  `RoundState`) is imported as `import type`, which esbuild erases entirely — only the one
  runtime value needed its own home. This was caught by the build step itself (§13) failing
  loudly, not discovered by inspection.
- **RunController**: `getJournal(runId)` / `getJournalEntry(request)`, same shape as
  `getSessionArtifacts`/`getExecutionOutput` (redacts the entry text with `redactSecrets`
  again on the way out, defense in depth, since reports/reviews aren't otherwise redacted
  before crossing into the renderer).
- **BridgeEngine**: `getJournal(runId)` regenerates the journal first (unless the session
  is the *live* `RUNNING` one — then the run host's own background rebuild owns it) and
  returns `readJournalIndex`; `getJournalEntry(runId, kind, iteration)` reads one fixed
  file by name (never a caller-supplied path).
- **Live regeneration**: inside `runLoop`, a serialized queue (`journalQueue`) rebuilds the
  journal at safe checkpoints — after `REPORT_VALIDATED` (a round just finished) and at
  `CLAUDE_EXECUTING` for iteration > 1 (the previous round's review just landed) — and is
  awaited once more at the very end of the run. A journal failure never fails the run
  (`.catch(() => {})`); rebuilds never overlap (each `.then()` chains onto the last).

## 12. Renderer UI

- **JOURNAL tab** (`ArtifactViewer` → `JournalPanel`): one `getJournal` call renders the
  rounds list (state mark ✓/→/✗/…, decision, and a button per available entry: Claude
  Report / ChatGPT Review / Claude Prompt / Next Prompt) plus Session Index and FINAL
  REPORT buttons when present. **Nothing is fetched until clicked** — selecting an item is
  the only thing that triggers `getJournalEntry`, and exactly one entry is in flight at a
  time (verified in `tests/desktop/renderer/execution.test.tsx`: zero `getJournalEntry`
  calls before any click, exactly one after).
- **CHATGPT RESPONSE tab**: now a three-way toggle — **Raw** (the untouched
  `NNN-chatgpt-review.md`, unchanged from M4), **Review** (the same `LazyJournalEntry` the
  JOURNAL tab uses, fetching `CHATGPT_REVIEW` for the selected iteration), **Next Prompt**
  (the already-loaded `extractedPrompt` artifact — no extra round-trip, since
  `SessionArtifacts` already carries it).
- **StartRunDialog**: added read-only `Developer`/`Reviewer` fields (informational —
  "Claude Code CLI (executor)" / "Codex CLI (ChatGPT sign-in)"; this is not a choice, by
  design — AI Bridge only ever drives these two CLIs) and the preset/custom "Maximum
  review rounds" select from §3.
- **ExecutionPanel**: token usage lines already existed as part of the execution record
  view; M4.2's `usage` field flows through the same display path, showing `UNKNOWN` when
  the CLI reported none.

## 14. Recovery

Journal rebuild is a pure read-then-write over already-durable artifacts — it never
participates in the crash-recovery decision itself (`decideRecoveryStrategy` is
unchanged). After a resume, the run host's own rebuild queue picks up again at the next
`REPORT_VALIDATED`/`CLAUDE_EXECUTING` checkpoint; `BridgeEngine.getJournal()` also
rebuilds on demand for a non-live session, so opening the JOURNAL tab on a session that
crashed mid-round still shows an accurate, non-duplicated rounds list (`readJournalIndex`
derives rounds straight from `SessionArtifacts.iterations`, which is itself crash-safe —
see M4.1). Verified in `tests/journal.test.ts`: forcing a checkpoint back to
`REPORT_VALIDATED` at iteration 2 and resuming produces exactly rounds 1–3 on disk, no
duplicate `NNN-claude-report.md`/`NNN-review.md` files.

## 15. Security

Unchanged posture, extended consistently:

- `getJournalEntry` validates `runId` (path-traversal-safe pattern, same as every other
  channel) and `kind` (must be one of the seven literal `JournalEntryKind` values) before
  ever touching the filesystem; the resulting file name is always one of seven fixed
  strings, never built from caller input.
- Entry text is redacted again in `RunController` before crossing into the renderer
  (`redactSecrets`), matching the existing defense-in-depth pattern for CLI output.
- The Markdown renderer still never executes HTML/script from a report or review — this
  was true before M4.2 and is unchanged (verified again by
  `tests/desktop/renderer/markdown.test.tsx`, including a new case with a malicious
  `<script>`/`onerror` payload embedded via `FAKE_CLAUDE_REPORT_EXTRA`, confirmed preserved
  as literal text — see `tests/journal.test.ts`).
- Links render as real anchors but can never navigate (`preventDefault()` always wins —
  verified via `dispatchEvent`'s return value, since React's delegated `onClick` only runs
  in the bubbling phase).
- No new credentials, no new network access, no new IPC surface beyond the two typed
  channels above (still 17 total, up from 15) — see the existing `security.test.ts` suite,
  unmodified and still passing.

## 16. Limitations

- The "Major Development Phases" section of the final report only lists what Codex chose
  to label under `## Development Phase` — if a reviewer never writes that heading for any
  round, the section is simply empty (labelled, not fabricated).
- "Problems Resolved" and "Architecture Summary" are always reported as not
  inferred/not generated (§7) — by design, not an oversight; AI Bridge doesn't have a
  reliable signal for either without asking a model to guess, which the spec forbids.
- Mermaid text renders as a plain code block, not an interactive diagram (§10) — matches
  "Mermaid optional" in the spec; no diagram library was added.
- A live-`RUNNING` session's JOURNAL tab reflects the last *checkpointed* rebuild
  (§11/§14), not literally every keystroke of a round in progress — this matches how
  every other read-only artifacts view already behaves (M4/M4.1), not a new gap.
- No dedicated `real-e2e.ts` "journal" scenario script was added; the real integration
  test (§13) was run directly through the CLI rather than through a new scripted Electron
  scenario. The desktop-specific journal code paths (IPC, preload, `JournalPanel`) are
  covered by the fake-CLI-backed test suite and by the smoke test's preload-surface
  check, not by a real-CLI-driven Electron E2E run.
