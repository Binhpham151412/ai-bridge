## BridgeEngine

`src/core/bridge-engine.ts` — the real Core entry point the M3 report's biggest gap asked
for. `BridgeEngine` owns exactly what `cli.ts`'s `runLoop` used to own directly: doctor
gating, the run lock, session directory creation (via `SessionManager`), Orchestrator
construction and wiring (adapters, crash injection, cooperative stop/pause), and state
persistence (via `AtomicJsonWriter`). One instance is scoped to one project directory;
stateless between calls (every method re-reads `.ai-bridge/state/` fresh).

Deliberately **not** split into `SessionFactory`/`AdapterFactory`/`StateManager`/
`LockManager`/`RecoveryManager` sub-classes, despite the spec offering that shape as an
option — a single project/single-run scope doesn't need that separation yet, and
splitting it now would be abstraction without payoff (echoing this project's own
"simplicity first" convention). If a second real caller ever needs a genuinely different
composition of these pieces, that's the point at which splitting would earn its cost.

Testability: `BridgeEngine` takes an optional `BridgeEngineDeps` (constructor's second
argument) — `runDoctor` (full preflight override), `isPidAlive`, `attemptGracefulStop`,
`claudeCommandArgsPrefix`/`codexCommandArgsPrefix` (test-only fake-CLI wiring), and
`claudeEnv`/`codexEnv` (test-only fake-CLI env vars) — all defaulting to real
implementations, mirroring the same "inject the seam, real defaults at the outermost
layer" convention already used throughout this codebase (`loadConfig`, `checkGitStatus`,
`runDoctorChecks`). One real bug was caught and fixed *before* it ever shipped, purely by
reasoning about this default: an initial `claudeEnv: {}` default would have made
`child_process.spawn` **replace** the child's entire environment (no `PATH`, no
`APPDATA`, ...) instead of inheriting it, since Node only inherits `process.env` when
`env` is omitted entirely, not when it's `{}` — breaking the real `claude`/`codex` CLI in
production. Fixed by defaulting to `undefined`, never `{}`.

## Core API

```typescript
class BridgeEngine {
  constructor(projectPath: string, deps?: BridgeEngineDeps);
  doctor(): Promise<DoctorReport>;
  start(options: BridgeStartOptions): Promise<BridgeRunOutcome>;
  resume(): Promise<BridgeRunOutcome>;
  pause(): Promise<BridgePauseOutcome>;
  stop(): Promise<BridgeStopOutcome>;
  status(): Promise<BridgeStatus>;
  logs(lines?: number): Promise<string[]>;
  reset(): Promise<BridgeResetOutcome>;
  subscribe(listener: (event: BridgeEvent) => void): () => void;
}
```

Full contract (every type, every field, the error model) is in
[docs/10-electron-integration-contract.md](10-electron-integration-contract.md) — not
duplicated here. One deliberate deviation from the spec's suggested shape:
`start()`/`pause()`/`resume()`/`stop()` return **typed outcomes** (discriminated unions),
not bare `Promise<void>` — a caller needs to know *what happened* (blocked? already
running? completed with what status?) without a second round-trip to `status()`. Exit
codes are never part of these types — that mapping stays entirely in `cli.ts`, so
Electron is structurally prevented from ever depending on a CLI exit code (directly
addressing spec §16's warning).

## CLI Refactor

`src/cli.ts` shrank from ~745 lines (doctor logic, run-loop wiring, state writing, event
logging, pause/resume/stop/reset logic — nearly everything) to a thin adapter: parse argv
→ construct one `BridgeEngine` → call its method → map the typed outcome to console
output and an exit code. Verified structurally, not just by inspection: an architecture
test (`tests/architecture.test.ts`) greps every file under `src/core/`, `src/adapters/`,
`src/reports/`, `src/prompts/` for an import of `cli.ts`/`cli-args.ts`, any `console.*`
call, or any direct `process.exit()` call (with block/line comments stripped first, so a
doc-comment mentioning `process.exit()` in prose doesn't false-positive) — all three
checks pass, and a fourth test confirms `cli.ts` is the one importing `bridge-engine.ts`
(not the reverse).

One CLI-level exit-code refinement made possible by this refactor: `pause`'s
`STILL_RUNNING`/`ENDED_BEFORE_PAUSE` outcomes now set `process.exitCode = 1` (previously
both fell through to the default `0`, an M3-flagged gap) — `PAUSED` alone is exit `0`.
This is CLI-only cosmetic; Electron never sees or depends on it (it gets the typed
`BridgePauseOutcome` directly).

## Event API

`EVENT_TYPES` (unchanged set from M3, already includes `PAUSE_REQUESTED`/`PAUSED`) is now
exposed live via `BridgeEngine.subscribe(listener)`, not just written to
`events.jsonl`/`ai-bridge.log`. Every `logEvent` call notifies all current subscribers
synchronously (listener exceptions are caught and swallowed — one broken subscriber can
never break a run or other subscribers) *in addition to* the existing durable file
writes — a UI gets true real-time updates without ever polling or tailing a file.

## Status API

`BridgeStatus` (`core/bridge-engine.ts`) is the same data `cmdStatus` used to print,
now returned as a plain object instead of printed lines: `runId`, `status`
(`NOT_STARTED`/`RUNNING`/`INTERRUPTED`/a terminal status), `iteration`, `currentPhase`,
`claude`/`codex` (`{pid, sessionId|threadId}`), `startedAt`/`updatedAt`,
`lastReportPath`. Never throws for "no session" — resolves with `status: 'NOT_STARTED'`,
safe to poll on a timer.

## Recovery

Unchanged decision logic (`core/recovery/recovery.ts`'s `decideRecoveryStrategy`) — now
called from exactly one place, `BridgeEngine.resume()`, with `cli.ts`'s `cmdResume`
reduced to constructing a `BridgeEngine` and calling `resume()`. There is no second
implementation anywhere for Electron to accidentally diverge from.

## Pause / Resume

Unchanged mechanism (cooperative marker file, checked only at safe boundaries) — now
exposed as `BridgeEngine.pause()`/`resume()`, returning typed outcomes instead of printed
text. Proven for real through `BridgeEngine` directly (not the CLI) — see Real Integration
Tests below.

## Integrity

Unchanged report-transport/prompt integrity checks (M3), **plus a new per-iteration audit
artifact** added this sprint per spec §12: `<sessionDir>/<NNN>-integrity.json`:

```json
{
  "iteration": 1,
  "claudeInputHash": "…", "reportHash": "…",
  "codexInputHash": "…", "codexResponseHash": "…", "promptHash": "…"
}
```

Written once per iteration, immediately after the extracted prompt is persisted — an
independently-inspectable audit trail (not a new verification mechanism; the existing
in-flight checks already enforce these hand-offs are correct). Verified by two tests
(`tests/iteration-integrity-chain.test.ts`): every hash matches the actual on-disk
artifact by direct recomputation, and a mutation check confirms the stored value is a
real content digest, not a placeholder.

**Real bug found and fixed via this exact addition, through real testing (not the unit
tests above — those passed on the first try):** the `AFTER_PROMPT_PERSISTED`
crash-injection point (M3) fired *before* checking whether Codex's own verdict was
`DONE`/`NEED_HUMAN`. A real M3.5 crash-recovery test that happened to hit a real `DONE`
verdict crashed there anyway, and `resume()` then fed Claude the closing remark
("Task is complete...") as if it were a work instruction — Claude correctly did nothing
new, producing `REPORT_INVALID`. The recovery *mechanism* itself was flawless (SHA-256
of the pre-crash prompt matched exactly what Claude received) — the bug was that this
crash point could fire for a case where there was never a "next Claude call" to crash
before. Fixed by moving the `DONE`/`NEED_HUMAN` branch before the crash check (so it's
now unreachable for those verdicts), covered by 3 new tests
(`tests/crash-injection.test.ts`), and **re-verified twice for real**: once confirming
the crash correctly no longer fires for a real `DONE` verdict (exit code 0, not 137),
once confirming a real genuine `CONTINUE` verdict still crashes, resumes, and completes
correctly (see Real Integration Tests).

## Process Safety

Unchanged this sprint (`process-manager.ts`, `run-lock.ts`) — `BridgeEngine.stop()` calls
the same `requestStop` cli.ts used to call directly. Additionally hardened per spec
§13-14:

- **`runProcess` (`automation/process-runner.ts`) gained `maxBufferBytes`** (default
  50MB per stream — far larger than any real single Claude/Codex CLI call's output).
  Once a stream's accumulated bytes exceed the cap, further chunks are dropped (not
  buffered) and `stdoutTruncated`/`stderrTruncated` is set; the process itself keeps
  running normally (timeout/cleanup unaffected). 4 new tests, including one proving a
  real timeout-kill still works with a cap set, and one proving the default is generous
  enough that normal-sized real output is never truncated.
- **`ReportValidator.validateFile` now `stat()`s before `readFile()`s.** Previously the
  entire file was read into memory before its size was checked against `maxBytes` — a
  pathologically large file would still be fully buffered before rejection. Now rejected
  by size alone, before any read. 4 new tests (normal, exactly-at-limit, over-limit,
  missing-file).
- **`events.jsonl`/`ai-bridge.log` now rotate** via a new `rotateIfOversized(filePath,
  maxBytes)` (`core/observability/events.ts`) — a simple current→`.1` rotation (spec's
  own suggested scheme), wired into `BridgeEngine.logEvent` with a 10MB-per-file default.
  Bounds long-running-project log growth to ~2x the cap instead of unbounded. 5 new
  tests.

**Test 1 (normal workflow):** Multiple real single/multi-iteration runs completed with
real Claude execution, real report validation, real Codex review, and real session/thread

## Crash Recovery Test

`sandbox/m3.5-recovery-test/`, `AI_BRIDGE_CRASH_AT=AFTER_PROMPT_PERSISTED`, driven entirely
through `BridgeEngine.start()`/`resume()` directly:

1. First real attempt: real Codex verdict was `DONE`. This is exactly the scenario that
   surfaced the bug described under Integrity above (`REPORT_INVALID` on resume).
2. After the fix: re-ran the identical scenario — the process exited **normally (code 0,
   `finalStatus: DONE`)**, proving the crash point correctly no longer fires when there's
   no next Claude call to crash before.
3. Re-ran with a task structured to give Codex genuine grounds for `CONTINUE` (an
   explicit two-part task, part 2 deferred) — real crash (exit code 137) at
   `AFTER_PROMPT_PERSISTED`. Verified before resuming: `sha256(001-extracted-prompt.md)
   == 001-integrity.json's promptHash`. Called `BridgeEngine.resume()` directly (fresh
   engine instance, no CLI): same Claude session and Codex thread reused, iteration 2's
   prompt file hashed to the **exact same SHA-256** as the pre-crash value, Claude
   genuinely implemented the deferred work (`subtract`, preserving `add`), `finalStatus:
   DONE` at iteration 2.

Result: **PASS**, with one real bug found and fixed along the way, and the fix itself
re-verified against the real scenario that originally exposed it (both the now-inert and
the still-correctly-crashing paths).

## Pause/Resume Test

`sandbox/m3.5-pause-test/`, driven entirely through `BridgeEngine` directly: `start()` in
the background, `pause()` called almost immediately (real Claude PID confirmed alive
first via `status()`). First attempt: the real round-trip completed faster than the pause
request could land — `pause()` correctly reported `ENDED_BEFORE_PAUSE` with
`finalStatus: DONE` (an honest negative result, not a false success). Second attempt
(same task shape, called `pause()` sooner): `pause()` returned `PAUSED` after real
iteration 1 (Claude + Codex) completed for real; `status()` confirmed `PAUSED`, session
and thread ids present. Verified: `sha256(001-extracted-prompt.md)` matched exactly.
Called `resume()` directly: same session/thread reused, Claude genuinely implemented the
deferred `divide` function while preserving `multiply`, `finalStatus: DONE` at
iteration 2.

Result: **PASS**. Confirms pause is genuinely cooperative (never interrupted a live
Claude/Codex call — both negative and positive real outcomes were observed and both were
handled honestly) and that resume-from-pause and resume-from-crash share the exact same
underlying mechanism, as designed.

## Remaining Limitations

1. **No formal audit-chain field distinguishing a `CONTINUE` chain from a `DONE`/
   `NEED_HUMAN` one.** The integrity-chain artifact is written identically regardless of
   verdict — a consumer reading it can't tell from the artifact alone whether
   `promptHash` represents "the next real instruction" or "a closing remark." Not a
   safety issue (the orchestrator's own control flow already handles this correctly
   after the M3.5 fix), but worth a `parsedStatus` field in a future pass.
2. **No log rotation beyond one backup file (`.1`).** Bounds growth to ~2x the cap, not
   to a fixed absolute ceiling across arbitrarily many rotations — acceptable per the
   spec's own "don't turn this into a logging project" guidance, but a caller running one
   project for months without ever restarting could still see `events.jsonl.1` itself
   eventually need attention (extremely unlikely in practice; sessions are naturally
   bounded by `maxIterations`).
3. **`pause`'s `STILL_RUNNING`/`ENDED_BEFORE_PAUSE` CLI exit codes are both now `1`**
   (previously both `0`, an M3 gap) — collapsed into one non-success code rather than
   split into two distinct new codes, to avoid expanding the CLI's exit-code convention
   further. Electron doesn't need this distinction anyway (it reads the typed
   `BridgePauseOutcome` directly).
4. **`SessionManager`'s `sessionId` counter and `run-lock`'s lock file remain
   per-project, not per-machine** — unchanged from M2/M3, still out of scope.
5. **Real Codex's own judgment, not this sprint's code, determined how many of the real
   integration-test runs needed 2 iterations.** Every attempt at Test 1 alone reached
   genuine `DONE` in 1 iteration; the 2-iteration Claude→Codex→Claude→DONE shape was
   fully and rigorously proven by Tests 2 and 3 instead. Documented as a real observation
   about this session's real Codex behavior, not a gap in AI Bridge.
