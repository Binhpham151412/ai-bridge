# AI Bridge — M4.2 Development Journal & Custom Review Rounds Report

## Executive Summary

M4.2 adds two features on top of the M4/M4.1 Electron desktop app without touching its
orchestration, recovery, or security model: (1) a per-run, validated, safety-capped choice
of how many review rounds a run may take ("Maximum review rounds", 1–100, preset select +
Custom), and (2) a Markdown **Development Journal** generated from artifacts Core already
writes and verifies — a Claude report and a ChatGPT review per round, a session index, and
a final whole-session report, all viewable in a new JOURNAL tab with a small, safe,
hand-rolled Markdown renderer. All work reuses the existing `BridgeEngine` / Core /
Electron Main / preload / React architecture; no new orchestration system, no API keys, no
cloud services were introduced. **462/462 tests pass**, both TypeScript configs are clean,
the desktop app builds and packages, and one real, unfaked integration run (real Claude
subscription + real ChatGPT-signed-in Codex) completed successfully and is documented below
byte-for-byte.

## Baseline

Before this milestone: M4 (Electron + React desktop app) and M4.1 (Session & Execution
Transparency) were both complete and verified — 438/438 tests passing, per-call Claude/
Codex execution records (session ids with evidence levels, pids, exit codes, stdin
delivery, redacted stdout/stderr tails), and a read-only Sessions/Artifacts viewer. `.ai-
bridge/sessions/<id>/` already held `NNN-claude-prompt.md`, `NNN-chatgpt-review.md`,
`NNN-extracted-prompt.md`, `NNN-integrity.json`, and the M4.1 execution-record/CLI-output
files. `maxIterations` was already a per-run option persisted into `current-session.json`
(so resume already preserved it), but had no UI beyond a raw number field, no explicit
validated safety cap, and no `INVALID_OPTIONS` outcome for out-of-range input.

## Architecture Changes

None at the orchestration layer. `Orchestrator`, `SessionManager`, the state machine
(`core/state-machine`), `decideRecoveryStrategy`, `run-lock`, and the IPC router are
byte-for-byte unchanged. New code:

- `src/core/journal/journal-types.ts` — new, zero-import file: `JOURNAL_ENTRY_KINDS`
  (7-value tuple) + `isJournalEntryKind`. Exists solely so the renderer's browser-platform
  esbuild bundle can use these two runtime values without pulling in `journal.ts`'s
  `node:fs/promises`/`node:path` imports (see "Files Changed" and the build failure this
  caused, described under Tests).
- `src/core/journal/journal.ts` — new: pure Markdown renderers (`renderClaudeReport`,
  `renderReview`, `renderSessionIndex`, `renderFinalReport`) plus the idempotent
  filesystem layer (`buildJournal`, `readJournalIndex`, `readJournalEntry`).
- `BridgeEngine.getJournal` / `getJournalEntry` (new methods) + a serialized,
  non-fatal journal-rebuild queue inside `runLoop`, scheduled at safe transitions
  (`REPORT_VALIDATED`, `CLAUDE_EXECUTING` for iteration > 1) and awaited once more at run
  end.
- `BridgeEngine.start()` gained an `INVALID_OPTIONS` outcome kind, checked before
  preflight/lock acquisition, for a `maxIterations` outside `[1, 100]`.
- Two new IPC channels, `RunController` methods, preload functions, and one new React
  component (`JournalPanel.tsx`) plus one new tab (`JOURNAL`) and a 3-way toggle on the
  existing `CHATGPT RESPONSE` tab.

## Custom Review Rounds

- `MAX_RUN_ITERATIONS = 100` (Core) and `MAX_ITERATIONS_LIMIT = 100` (desktop IPC contract)
  — the one safety ceiling, enforced in `BridgeEngine.start()` and again in the IPC
  validator.
- `start({ maxIterations })` outside `[1, 100]` (non-integer, ≤ 0, or > 100) →
  `INVALID_OPTIONS` — refused before any lock/session is created (verified: no session
  directory exists after a rejected `start()`, see Tests).
- Resume preserves the exact `maxIterations` the run was started with (already true since
  M4; verified again for M4.2's stricter validation path).
- CONTINUE at the final iteration → `STOPPED_MAX_ITERATIONS`, and iteration N+1 genuinely
  never starts (verified: no `00N+1-claude-prompt.md` file is ever written).
- DONE at any iteration (1, 2, or the final one) stops immediately with that exact
  iteration count, regardless of the configured cap.
- Desktop UI: preset select (1/2/3/5/10/20/30/50/Custom…) plus Developer/Reviewer
  informational fields, exact hint text "Maximum rounds — run stops earlier if reviewer
  returns DONE."

## Journal Architecture

Reuses the existing `.ai-bridge/sessions/<runId>/` directory; adds four new file kinds per
session (`NNN-claude-report.md`, `NNN-review.md`, `session.md`, `final-report.md`) next to
the artifacts M2–M4.1 already write. Generation is **idempotent** (`writeIfChanged`: temp
file + atomic rename, skipped when content is unchanged) so pause/resume/crash-recovery
never produces a duplicate or partially-written round. `final-report.md` is written exactly
once, only when the run reaches a final status (`DONE`/`NEED_HUMAN`/`ERROR`/`STOPPED`/
`STOPPED_MAX_ITERATIONS`).

## Claude Report

`NNN-claude-report.md`: session metadata from the (already-verified) M4.1 execution record
— Claude CLI session id + evidence level, continuity verdict on resume, exit code, start/
end/duration, exact prompt SHA-256/bytes, token usage, and the integrity-hash match note —
followed by the validated report **verbatim**. Nothing is summarized or reworded.

## ChatGPT Review

`NNN-review.md`: same metadata style for the Codex side (thread id + evidence, token
usage), followed by **`## Review (Codex, verbatim)`** — Codex's own narrative Markdown
(the text outside the `<AI_BRIDGE_RESPONSE>` block, now explicitly requested by the updated
reviewer-input contract), then **`## Decision`** (the parsed `STATUS`, from the existing
authoritative parser — never re-derived) and **`## Next Prompt`** (the exact next prompt,
with a note on whether it was actually sent).

## Final Report

Sections, in the exact order the spec listed: Task, Session, Executive Summary,
Development Timeline (per iteration), Major Development Phases, Files Changed, Tests,
Important Decisions, Problems Encountered/Resolved, Remaining Work, Known Risks,
Architecture Summary, Interaction Timeline (verdict chain + a Mermaid flowchart, rendered
as a fenced code block — no diagram execution), Final Result. Everything sourced from
Claude's reports and Codex's reviews is labelled "as reported by Claude" / "as reviewed by
Codex"; "Problems Resolved" and "Architecture Summary" are always explicitly marked as not
inferred/not generated rather than guessed.

## Markdown Viewer

`lib/Markdown.tsx` gained blockquotes, horizontal rules, and `[text](url)` links (rendered
as real `<a>` elements with `href="#"` plus an unconditional `preventDefault()` — verified
via `dispatchEvent`'s return value, since React's delegated `onClick` only fires in the
bubbling phase and a same-node listener would observe the event too early). No HTML/script
execution path was added or exists; a report containing `<script>`/`onerror` payloads is
still shown as literal text (re-verified with a new malicious-content journal test). Fenced
code with an unrecognized info string (e.g. `mermaid`) renders as plain code, never as an
executed/rendered diagram.

## UI Changes

- New **JOURNAL** tab in the Artifacts panel: a rounds list (state mark, decision, and a
  button per available entry — Claude Report / ChatGPT Review / Claude Prompt / Next
  Prompt), plus Session Index and FINAL REPORT buttons. Confirmed lazy: zero
  `getJournalEntry` calls before any click, exactly one after each click.
- **CHATGPT RESPONSE** tab is now a 3-way toggle: Raw (unchanged, the untouched CLI
  output) / Review (the human-readable journal review) / Next Prompt (the exact next
  prompt, no extra round-trip).
- **StartRunDialog**: read-only Developer/Reviewer fields, and the "Maximum review rounds"
  preset/custom select described above.
- Token usage rows already existed in `ExecutionPanel` (M4.1); M4.2's parsed `usage` field
  flows through unchanged, showing `UNKNOWN` when a CLI reported none.

## Token Usage

Parsed once, from real CLI output only:

- Claude: the stream-json `result` event's `usage` object (`input_tokens`,
  `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`); total = sum
  of all four.
- Codex: the last `turn.completed` event's `usage` object (`input_tokens`,
  `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`,
  `reasoning_output_tokens`); total = input + output.
- Missing/unparseable usage → `ExecutionRecord.usage = null` → journal shows **UNKNOWN**,
  never an estimate, never zero. Real usage was independently verified in the real
  integration test (below): Claude reported 168,163 total tokens, Codex reported 16,822.
- Explicitly labelled as per-call usage — never presented as, or conflated with, account
  quota.

## Recovery

Journal rebuild never participates in the crash-recovery decision (`decideRecoveryStrategy`
is unchanged) — it is a pure, idempotent read of already-durable, already-recovery-safe
artifacts (`SessionArtifacts`/`SessionSummary`, both M4.1-proven). Forcing a session back to
a `REPORT_VALIDATED` checkpoint at iteration 2 and resuming (fake CLIs, deterministic)
produced exactly rounds 1–3 on disk with no duplicate `NNN-claude-report.md`/`NNN-review.md`
files — verified in `tests/journal.test.ts`.

## Security

- `getJournalEntry`'s `runId`/`kind` are validated against a fixed pattern / a 7-value
  enum before any filesystem access; the resulting file name is always one of seven literal
  strings, never built from caller input (no path traversal surface).
- Journal entry text is redacted again (`redactSecrets`) in `RunController` before crossing
  into the renderer, matching the existing CLI-output redaction pattern.
- No new credentials, no new network access, no new IPC channel beyond the two typed and
  validated ones added (17 channels total, up from 15). The existing `security.test.ts`
  suite (renderer sandboxing, CSP, no eval, no remote module, Core→Desktop one-way
  dependency, no duplicated process-management logic) is unmodified and still passes in
  full.

## Known Limitations

- "Major Development Phases" only lists what Codex explicitly labels under `##
  Development Phase`; not every round is guaranteed to have one.
- "Problems Resolved" and "Architecture Summary" are always reported as UNKNOWN/not
  generated, by design — no attempt is made to infer either.
- Mermaid text in the final report renders as a plain code block, not an interactive
  diagram (matches the spec's "Mermaid optional").
- A live-`RUNNING` session's JOURNAL tab reflects the last checkpointed rebuild, not
  every in-progress keystroke — consistent with how every other read-only artifacts view
  already behaves.
- No dedicated `scripts/desktop/real-e2e.ts` "journal" scenario was added; the real
  integration test above was run directly via the CLI rather than through a new scripted
  Electron E2E scenario. The desktop-specific journal code (IPC/preload/`JournalPanel`) is
  covered by the fake-CLI test suite and the smoke test's preload-surface check instead.
