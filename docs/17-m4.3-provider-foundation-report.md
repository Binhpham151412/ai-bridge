# AI Bridge — M4.3 Phase 1 Provider Foundation Report

Date: 2026-09-27. Scope: Provider core + CLI discovery only. No UI.

## 1. Summary

M4.3 Phase 1 adds a typed, backend-only provider diagnostics module
(`src/core/providers/`) for **Claude Code** and **ChatGPT / Codex**. It can determine:

- whether each CLI is installed, and the real executable path
- its version
- its authentication state and login method
- the account/plan, but only when the official CLI prints them
- readiness, kept separate from installation and authentication
- usage-limit (quota) conditions, through an opt-in minimal execution probe

A `ProviderRegistry` provides lookup, explicit cached-vs-refresh reads, in-flight dedupe,
a guard timeout, a non-executing login-command descriptor, and runtime registration of
future providers.

Nothing else changed. BridgeEngine, the Orchestrator, both execution adapters, the doctor,
cost-guard, IPC/preload and the renderer are untouched (§3). No credentials are read or
stored, no API keys or API calls were introduced, and nothing automates a browser.

Validation (final runs): `pnpm test` **535/535 pass**, of which 59 tests are new.
`pnpm typecheck` is clean for both configs, and `pnpm build` succeeds.

## 2. Architecture

The design is documented in [16-m4.3-provider-manager-foundation.md](16-m4.3-provider-manager-foundation.md). In brief:

- `ProviderAdapter { descriptor, diagnose(ctx, depth), loginCommand(exe) }` is the only
  contract the registry depends on.
- `createCliProviderAdapter(CliProviderSpec)` runs one shared pipeline for CLI providers:
  discover → version → auth → environment → optional probe. Claude Code and Codex are
  declarative specs plus small parsers.
- `ProviderDiagnosticContext` injects executable lookup, process spawn (the existing
  `runProcess`), env, timeouts and clock. Tests swap in real fake-CLI processes.
- There are two depths:
  - `status` (default) runs `--version` plus the auth-status command and spends no quota.
  - `execution` also runs one tool-less "reply OK" probe, which spends a small amount of
    quota and is the only way a usage limit can be observed.

## 4. Claude provider implementation

`createClaudeCodeProvider()` (`claude-code-provider.ts`):

- Discovery: `where claude`, preferring the first `.exe`.
- Version: `claude --version`.
- Auth: `claude auth status`.
- Probe: `claude -p --output-format json --no-session-persistence --tools ""`, with the
  prompt on stdin and the OS temp dir as cwd.
- Login descriptor: `claude auth login --claudeai`.
- Cost-risk env: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`.

Observed on this machine (read-only commands, 2026-09-27):

- `where claude` returned `…\.local\bin\claude.exe`, then an extension-less
  `…\AppData\Roaming\npm\claude` shim, then `claude.cmd`. This is why discovery prefers
  `.exe`.
- `claude --version` → `2.1.161 (Claude Code)`, exit 0.
- `claude auth status` → `{"loggedIn":false,"authMethod":"none","apiProvider":"firstParty"}`
  with **exit code 1**. The parser therefore reads the JSON before judging the exit code.
- `claude --help` lists `--no-session-persistence` and `--tools` ("Use "" to disable all
  tools") in 2.1.161.

`parseClaudeAuthOutput` requires a JSON object with a boolean `loggedIn`, maps the login
mode through the existing `parseClaudeAuthStatus`, and allow-lists a validated `email` and a
validated `subscriptionType`.

## 6. Authentication detection

Each provider's CLI output maps to these fields:

- `authentication.status`: `AUTHENTICATED` / `NOT_AUTHENTICATED` / `UNKNOWN`
- `authentication.method`: `ACCOUNT_LOGIN` / `API_KEY` / `NONE` / `UNKNOWN`

The five cases in M4.3 §6 are distinguished through the `state` summary:

- `NOT_INSTALLED`
- `INSTALLED_NOT_AUTHENTICATED`
- `AUTHENTICATED`
- `AUTHENTICATED_BUT_NOT_READY` (API-key login, API-key env var, usage limit, or probe error)
- `UNKNOWN` (unparseable auth output or command failure)

**Real status-depth result on this machine** (`createDefaultProviderRegistry().getAllProviderStatuses()`,
2026-09-27, account value masked):

| Provider | installation | version | authentication | readiness | state |
|---|---|---|---|---|---|
| Claude Code | INSTALLED (`…\.local\bin\claude.exe`) | 2.1.161 | NOT_AUTHENTICATED / NONE | NOT_READY | INSTALLED_NOT_AUTHENTICATED |
| ChatGPT / Codex | INSTALLED (via `%LOCALAPPDATA%` fallback) | 0.155.0-alpha.16.4 | AUTHENTICATED / ACCOUNT_LOGIN, account `null`, plan `null` | READY (quota UNKNOWN) | AUTHENTICATED |

The Claude CLI reported itself logged out in this environment, so a **logged-in Claude
status against the real CLI was not verified** in this session. The logged-in parse path
(email and plan) is verified only against fixtures that follow the shape recorded in
M1 (`{"loggedIn":true,"authMethod":"claude.ai","subscriptionType":"pro"}`). No real Claude
output containing `email` was observed.

## 7. Readiness detection

Readiness is computed separately from installation and authentication; the full table is
in doc 16 §5.

- **READY at status depth** means: installed, account login, no API-key env var. Quota
  stays `UNKNOWN`, and the message says so ("Usage quota was not checked").
- **LIMITED** comes only from the execution probe, when the CLI's *error* text matches
  conservative usage-limit phrasing. `scope` is `WEEKLY` only if the CLI says "weekly".
- A generic `429 rate limit` or `500` error is `ERROR` / `PROVIDER_COMMAND_FAILED`, never
  `LIMITED`.
- Quota is never inferred from anything else.
- **The execution probe was not run against the real CLIs**, because it spends real
  quota. Its PASSED, LIMITED (weekly and unspecified), FAILED, TIMEOUT and INVALID paths are
  verified with fake CLIs only.

## 8. Security

- **No credential access.** Only `--version`, `auth status` / `login status` and the
  opt-in probe are run. No credential files, cookies, browser or UI automation are
  involved. Nothing is persisted; the cache is in memory only.
- **Allow-listed auth fields.** Token fields present in auth JSON are dropped. The test
  fixture `extra-secrets` includes `accessToken`/`refreshToken`, and the test asserts they
  are absent from the status.
- **All CLI text is redacted.** Any excerpt goes through `redactSecrets`, then is collapsed
  and truncated to 300 characters. Tests cover:
  - bearer tokens, `sk-ant-…` / `sk-proj-…` keys, `"accessToken"` / `"access_token"` /
    `"refresh_token"` JSON, and `ANTHROPIC_API_KEY=` assignments on stderr, across auth
    and probe failures for both providers
  - an adapter crash message containing a token
- **The redaction tests are proven to bite.** With `redactSecrets` temporarily removed
  from `safeExcerpt`, both redaction tests failed (2 failures out of 40). The file was then
  restored.
- **Env checks by name only.** Tests assert the variable name appears and the value never
  does.
- **The probe is never spawned** when the CLI is not logged in, uses an API-key login, or
  has a cost-risk env var set. A test asserts no `-p` invocation in those cases.
- **Core invariants hold.** No `console.*`, no `process.exit`, and no import from the
  desktop layer. The existing `tests/architecture.test.ts` and `tests/desktop/security.test.ts`
  pass with `src/core/providers/` included.

## 11. Known limitations

1. **Quota needs the probe.** Neither CLI's status command reports quota, so status-depth
   `READY` never implies quota is available (`quota.status: UNKNOWN`). The probe spends a
   small amount of quota and was not exercised against the real CLIs.
2. **Limit wording is pattern-based.** It is built from known CLI phrasing and tested with
   fixtures. Unfamiliar wording is reported as `ERROR` / `PROVIDER_COMMAND_FAILED` rather
   than `LIMITED`, so the failure mode is conservative. Reset times are not parsed.
3. **Claude account email is unverified against the real CLI.** It is read from an
   `email` field only when present. No real logged-in output was available in this
   environment.
4. **Codex exposes no account or plan.** Both are always `null`.
5. **No IPC, preload or UI wiring.** This is deliberate for Phase 1; the registry is not
   yet instantiated anywhere in the app.
6. **Discovery helpers are duplicated.** `where` and the `%LOCALAPPDATA%` fallback
   duplicate private helpers in `bridge-engine.ts`, so that BridgeEngine is untouched. The
   `.exe` preference applies only to provider diagnostics; BridgeEngine still uses the
   first `where` hit.
7. **Doctor quirk, left as is.** The existing doctor's Claude auth check reports a
   logged-out CLI as `FAIL — "claude auth status" exited 1`, not "not logged in", because
   it checks the exit code before parsing. The provider module handles this correctly.
   The doctor was not changed, since that is out of scope.
8. **Cache limits.** The cache is per registry instance and in memory, with no TTL.
   Callers refresh explicitly.
9. **Probe flags are only help-verified.** `--tools ""` and `--ephemeral` were confirmed
   in `--help` for the installed CLI versions but not run for real.

## 12. Future UI integration plan

This is the plan for the next milestone; none of it is implemented yet.

1. In Electron Main, create a single `createDefaultProviderRegistry()` for the app's
   lifetime.
2. Add typed IPC channels that map one-to-one onto registry methods:
   - `providers:list` → `listProviders`
   - `providers:get` → `getAllProviderStatuses()`, cached, spawning only the first time
   - `providers:refresh` → `{ refresh: true }` / `checkProvider(id)`
   - `providers:verify` → `checkProvider(id, { depth: 'execution' })`, with UI copy saying
     it uses a little quota
   - `providers:login-command` → `getLoginCommand(id)`
3. `ProviderStatus` is plain, structured-clone-safe JSON, so it crosses IPC unchanged.
4. The Provider screen reads cached status on open and refreshes only on explicit user
   action, never per render.
5. A `[ Login ]` button asks Main to launch the described interactive command in a visible
   console, only on explicit user action, then calls `checkProvider(id)`.
6. New providers (Grok, Cursor, DeepSeek, …) are added as a `CliProviderSpec` or a
   `ProviderAdapter` plus `register()`, with no change to the registry or the status model.
