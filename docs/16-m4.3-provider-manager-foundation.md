# AI Bridge — M4.3 Provider Manager Foundation (Phase 1)

Phase 1 of the Provider Manager: a backend-only, typed foundation for **discovering AI CLI
providers and diagnosing their installation, authentication and readiness**. There is no
UI in this phase, and the module is not wired into IPC, preload, BridgeEngine or the
Orchestrator. The execution flow (prompt delivery, review rounds, journal, recovery,
report validation, execution transparency) is unchanged.

All code lives in `src/core/providers/`:

| File | Purpose |
|---|---|
| `provider-types.ts` | Typed model: status enums, error codes, `ProviderStatus`, `ProviderAdapter`, `ProviderDiagnosticContext` |
| `executable-discovery.ts` | PATH-aware executable discovery (Windows-first) + Codex install-dir fallback |
| `cli-provider.ts` | Generic CLI diagnostic pipeline, readiness derivation, redaction, usage-limit detection |
| `claude-code-provider.ts` | Claude Code spec + parsers for `claude auth status` and the probe result |
| `codex-provider.ts` | Codex spec + parsers for `codex login status` and the probe's JSONL events |
| `provider-registry.ts` | `ProviderRegistry` (lookup, cache, refresh, in-flight dedupe, guard timeout), real-context and default-registry factories |

## 1. Provider architecture

```
ProviderRegistry ──holds──> ProviderAdapter { descriptor, diagnose(ctx, depth), loginCommand(exe) }
      │                          ▲
      │                          └── createCliProviderAdapter(CliProviderSpec)   ← Claude Code, Codex
      │
      └── ProviderDiagnosticContext { locateExecutable, runCommand, env, timeouts, probeCwd, now }
                 (real: where/which + %LOCALAPPDATA% fallback, runProcess, process.env)
                 (tests: node + fake CLI script via commandArgsPrefix)
```

- A **`ProviderAdapter`** is the only contract the registry knows about. It must resolve
  (never reject) with a complete `ProviderStatus`. The registry still guards against
  adapters that throw or hang.
- **`createCliProviderAdapter(spec)`** turns a declarative `CliProviderSpec` into an adapter.
  The spec contains the descriptor, version/auth/probe args, parsers, login args, and the
  cost-risk env keys. Claude Code and Codex are both specs over the same pipeline.
- **`ProviderDiagnosticContext`** is injected, so every side effect is replaceable in
  tests: executable lookup, process spawn, environment, timeouts and clock.
- Processes are spawned through the existing `runProcess` (`src/automation/process-runner.ts`).
  It uses no shell, kills the whole process tree on timeout, and caps buffers. Diagnostics
  cap each stream at 1 MB.

### Diagnostic pipeline (`diagnoseCliProvider`)

1. **discover**: `locateExecutable(executableName)`. If nothing is found, the result is
   `NOT_INSTALLED` and no process is spawned.
2. **version**: `<exe> --version`, then the first semver token is extracted. This step is
   informational: a failure is recorded as an error but does not decide readiness.
3. **auth**: the provider's auth-status command, handled by the provider's parser.
4. **environment**: checks whether a cost-risk API-key variable is present (presence
   only; values are never read or returned).
5. **probe**: runs only at depth `execution`, and only when the login is an account login
   and no cost-risk env var is set.

Each step can stop the pipeline with a typed error. See §5 for the readiness each one yields.

## 2. Provider registry

`ProviderRegistry` (see `provider-registry.ts`):

| Method | Spawns processes? | Behavior |
|---|---|---|
| `listProviders()` | no | Descriptors in registration order (copies) |
| `has(id)` | no | |
| `getCachedStatus(id)` | **never** | Last result or `null` |
| `getProviderStatus(id, { refresh? })` | only if nothing cached or `refresh: true` | Status-depth check |
| `checkProvider(id, { depth? })` | always | Fresh diagnosis; `depth` defaults to `'status'` |
| `getAllProviderStatuses({ refresh? })` | as `getProviderStatus`, per provider | Parallel, registration order |
| `getLoginCommand(id)` | **never** | Describes the official login command (see §7) |
| `clearCache(id?)` | no | |
| `register(adapter)` | no | Adds a provider; duplicate ids throw |

- **Unknown ids** throw (sync methods) or reject (async methods) with
  `UnknownProviderError` (`code: 'UNKNOWN_PROVIDER_ID'`, `providerId`).
- **Caching**: the cache is in memory, per registry instance, with no TTL. The caller
  decides explicitly between a cached read and a refresh. Nothing runs on construction.
- **In-flight dedupe**: concurrent `checkProvider` calls for the same `(id, depth)` share
  one diagnosis.
- **Copies**: every returned status is a `structuredClone`, so callers can't mutate the
  cache. Statuses are plain JSON, which makes them safe to send over IPC.
- **Guard timeout**: an adapter that never settles is cut off after `adapterTimeoutMs`
  (default `3 × statusTimeoutMs + probeTimeoutMs + 10 s`) and yields `readiness: 'ERROR'` /
  `PROVIDER_TIMEOUT`. An adapter that throws yields `readiness: 'ERROR'` /
  `PROVIDER_UNKNOWN` with a redacted detail.
- **Factories**: `createRealProviderContext(overrides?)` has these defaults: status
  commands 15 s, probe 120 s, probe cwd `os.tmpdir()`, `process.env`, real PATH lookup.
  `createDefaultProviderRegistry(ctx?, options?)` registers Claude Code, then Codex.

## 3. Claude Code diagnostics

| Step | Command | Parsing |
|---|---|---|
| discover | `where claude` | First `.exe` hit (see §8) |
| version | `claude --version` | `2.1.161 (Claude Code)` → `2.1.161` |
| auth | `claude auth status` (JSON is the CLI's default output) | See below |
| probe (opt-in) | `claude -p --output-format json --no-session-persistence --tools ""`, prompt on stdin, cwd = temp dir | Single `result` object |
| login (described only) | `claude auth login --claudeai` | Same hint the existing doctor prints |

**`claude auth status`.** The output is parsed as JSON **before** the exit code is judged:
the CLI exits **1** when logged out but still prints valid JSON (observed with 2.1.161). The
output must be a JSON object with a boolean `loggedIn`; anything else is
`PROVIDER_OUTPUT_INVALID` when the exit code is 0, or `PROVIDER_COMMAND_FAILED` otherwise.
The login mode comes from the existing cost-guard parser `parseClaudeAuthStatus`, so it
matches the doctor exactly:

| CLI | `authentication` |
|---|---|
| `loggedIn:false` | `NOT_AUTHENTICATED` / `NONE` |
| `loggedIn:true, authMethod:"claude.ai"` | `AUTHENTICATED` / `ACCOUNT_LOGIN` |
| `loggedIn:true, authMethod:"console"` | `AUTHENTICATED` / `API_KEY` |
| `loggedIn:true`, other `authMethod` | `AUTHENTICATED` / `UNKNOWN` |

- `account` is taken from the JSON `email` field only when it is present and shaped like an
  email address. It is never scraped from free text.
- `subscription` is taken from `subscriptionType` only when it is a short identifier
  (`^[A-Za-z0-9_-]{1,32}$`, lower-cased, e.g. `pro`).
- Every other field in the JSON, including any credential-shaped one, is ignored.

**Probe.** `is_error:false` with exit 0 is PASSED. Otherwise the error text is checked for
usage-limit phrasing (§6): the `result` field, stderr, and stdout when no result event was
found. A limit match gives LIMITED. A missing result event with exit 0 is
`PROVIDER_OUTPUT_INVALID`, and anything else is `PROVIDER_COMMAND_FAILED`. With `--tools ""`
the model gets no tools, so the probe cannot touch files. `--no-session-persistence` means
no session is saved.

**Cost-risk env keys:** `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`.

## 4. Codex diagnostics

| Step | Command | Parsing |
|---|---|---|
| discover | `where codex`, else newest `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe` | Same fallback BridgeEngine uses |
| version | `codex --version` | `codex-cli 0.155.0-alpha.16.4` → `0.155.0-alpha.16.4` |
| auth | `codex login status` | Plain text, printed to **stderr** (observed with 0.155) |
| probe (opt-in) | `codex exec --json -s read-only --skip-git-repo-check --ephemeral -`, prompt on stdin, cwd = temp dir | JSONL events |
| login (described only) | `codex login` | |

**`codex login status`.** The text is mapped by the existing cost-guard parser
`parseCodexLoginStatus`: "Logged in using ChatGPT" → `ACCOUNT_LOGIN`, "Logged in using an
API key" → `API_KEY`, "Not logged in" → `NOT_AUTHENTICATED`. Unrecognized text is
`PROVIDER_OUTPUT_INVALID` (exit 0) or `PROVIDER_COMMAND_FAILED` (exit ≠ 0). **Codex exposes
neither the account identity nor the ChatGPT plan**, so `account` and `subscription` are
always `null`, and the descriptor does not claim `reports-account`/`reports-subscription`.

**Probe.** A `turn.completed` event with exit 0 is PASSED. Otherwise the usage-limit check
(§6) runs over `error` event messages, `turn.failed.error.message`, and stderr.

**Cost-risk env keys:** `OPENAI_API_KEY`, `CODEX_API_KEY`.

## 5. Authentication and readiness states

`ProviderStatus` keeps installation, authentication, quota, execution check and readiness
as separate fields. Being installed never implies being ready.

| Field | Values |
|---|---|
| `installation` | `INSTALLED` · `NOT_INSTALLED` · `UNKNOWN` (adapter crashed/timed out) |
| `authentication.status` | `AUTHENTICATED` · `NOT_AUTHENTICATED` · `UNKNOWN` |
| `authentication.method` | `ACCOUNT_LOGIN` · `API_KEY` · `NONE` · `UNKNOWN` |
| `quota.status` | `AVAILABLE` (only after a passing probe) · `LIMITED` · `UNKNOWN` |
| `quota.scope` | `WEEKLY` (only if the CLI's text says "weekly") · `UNSPECIFIED` · `null` |
| `executionCheck.status` | `NOT_RUN` (status depth) · `SKIPPED` (execution depth, stopped earlier) · `PASSED` · `FAILED` · `LIMITED` |
| `readiness` | `READY` · `LIMITED` · `NOT_READY` · `ERROR` · `UNKNOWN` |
| `state` (summary) | `NOT_INSTALLED` · `INSTALLED_NOT_AUTHENTICATED` · `AUTHENTICATED` · `AUTHENTICATED_BUT_NOT_READY` · `UNKNOWN` |

Readiness is decided by the first step that stops the pipeline:

| Condition | readiness | error code |
|---|---|---|
| Executable not found | `NOT_READY` | `PROVIDER_NOT_INSTALLED` |
| Auth command timed out | `ERROR` | `PROVIDER_TIMEOUT` |
| Auth command failed (exit ≠ 0, unparseable) | `ERROR` | `PROVIDER_COMMAND_FAILED` |
| Auth output not in the documented shape (exit 0) | `UNKNOWN` | `PROVIDER_OUTPUT_INVALID` |
| Not logged in | `NOT_READY` | `PROVIDER_NOT_AUTHENTICATED` |
| Logged in, unrecognized method | `UNKNOWN` | `PROVIDER_OUTPUT_INVALID` |
| Logged in with an API key | `NOT_READY` | `PROVIDER_AUTH_MODE_UNSUPPORTED` |
| Cost-risk env var set | `NOT_READY` | `PROVIDER_AUTH_MODE_UNSUPPORTED` (step `environment`) |
| Depth `status`, all of the above OK | `READY`, quota `UNKNOWN` | none |
| Probe passed | `READY`, quota `AVAILABLE` | none |
| Probe reported a usage limit | `LIMITED` | `PROVIDER_QUOTA_LIMIT` |
| Probe timed out | `ERROR` | `PROVIDER_TIMEOUT` |
| Probe failed / output invalid | `ERROR` | `PROVIDER_COMMAND_FAILED` / `PROVIDER_OUTPUT_INVALID` |
| Adapter threw | `ERROR` | `PROVIDER_UNKNOWN` |
| Adapter exceeded guard timeout | `ERROR` | `PROVIDER_TIMEOUT` |

`state` is derived from these: `AUTHENTICATED` only when readiness is `READY`, and
`AUTHENTICATED_BUT_NOT_READY` for any other readiness of an authenticated provider.

**What status-depth `READY` means.** The CLI is installed, logged in with an account (not
an API key), and no API-key env var is set. It does **not** claim quota is available:
`quota.status` stays `UNKNOWN` and `diagnosticMessage` says "Usage quota was not checked."
Neither `claude auth status` nor `codex login status` reports quota, so status depth cannot
determine it.

Every non-fatal issue is still reported in `errors[]`. For example, a failing
`--version` adds a `version`-step error while readiness can remain `READY`.

## 6. Quota / usage limits

Limits can only be detected from the CLI's own error output during the opt-in execution
probe. `detectUsageLimit` is deliberately conservative:

- It matches "usage limit", "hit your (…) limit", "weekly / 5-hour / session / daily limit",
  "limit reached", and "quota exceeded/exhausted".
- It does **not** match a generic "rate limit" (a transient HTTP 429 throttle) or other API
  errors. Those are reported as `PROVIDER_COMMAND_FAILED`, never as `LIMITED`.
- It only ever runs on error text, never on a successful model answer.
- `scope` is `WEEKLY` only when the CLI's text contains "weekly". Reset times are not
  parsed, but the redacted CLI message is kept in `quota.detail`.

The probe spends a small amount of real quota: one tool-less single-turn prompt that asks
for "OK". It therefore never runs unless the caller passes `depth: 'execution'`.

## 7. Login actions (extension point only)

`getLoginCommand(id)` returns a **description** of the official login command:

```ts
{ executable: string | null, args: string[], displayCommand: string, interactive: true }
// claude-code → args ['auth','login','--claudeai'], displayCommand 'claude auth login --claudeai'
// codex       → args ['login'],                    displayCommand 'codex login'
```

It never executes anything. `executable` comes from the last cached check (`null` if the
provider was never checked or isn't installed). Both logins are interactive browser OAuth
flows. A future `[ Login ]` button must launch them only on explicit user action, in a
visible console, and then call `checkProvider` again. AI Bridge never automates the browser
or captures credentials.

## 8. Executable discovery

- Uses `where <name>` on Windows (`which -a <name>` elsewhere) with the **current
  environment's PATH**. No user path is hardcoded.
- **Prefers the first `.exe`** on Windows. `where claude` can also return the
  extension-less npm shim and `claude.cmd` (observed on this machine). Neither can be
  spawned without a shell, which AI Bridge never uses.
- For `codex` only, when PATH has no hit, the newest
  `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe` is used. The directory comes from the
  `LOCALAPPDATA` environment variable.
- `status.executable` is the real resolved path.

`executable-discovery.ts` intentionally duplicates the small `where`/fallback helpers that
are private to `bridge-engine.ts`, so that BridgeEngine is not modified. BridgeEngine's own
resolver (first `where` hit) is unchanged.

## 9. Security rules

- **No credentials touched.** Only the official status commands run. Nothing reads
  `~/.claude/.credentials.json`, `~/.codex/auth.json`, cookies or the browser. No API keys
  or API calls were introduced, and nothing is persisted: the cache lives in memory only.
- **Allow-list, not copy.** From auth output only `loggedIn`/`authMethod` (Claude), the
  login-mode sentence (Codex), a validated `email` and a validated `subscriptionType` are
  used. Other fields, including token fields a CLI might print, are dropped.
- **All CLI text is redacted.** Every excerpt that enters a status (`errors[].detail`,
  `quota.detail`, limit messages, adapter crash messages) goes through `safeExcerpt`: the
  existing `redactSecrets` masks API keys, bearer tokens, JWTs, credential JSON keys and
  auth headers, then whitespace is collapsed and the text truncated to 300 characters.
- **Env vars by name only.** The environment check reports variable names and never their
  values.
- **The probe can't bill an API key.** It is skipped unless the login is an account login
  and no cost-risk env var is set.
- **Core rules still hold.** No `console.*` and no `process.exit` in core
  (`tests/architecture.test.ts` covers `src/core/**`), and core has no dependency on the
  desktop layer.

## 10. Future UI integration contract

The next milestone can consume this module without changing it:

1. Electron Main (or the run host) creates **one** `createDefaultProviderRegistry()` and
   keeps it for the app's lifetime, so the cache is shared.
2. IPC handlers map one-to-one onto registry methods:
   - list → `listProviders()`
   - show cached → `getCachedStatus(id)` / `getAllProviderStatuses()` (spawns only the first time)
   - Refresh button → `getAllProviderStatuses({ refresh: true })` or `checkProvider(id)`
   - "Verify with a test prompt" (must say it uses a little quota) → `checkProvider(id, { depth: 'execution' })`
   - Login button → `getLoginCommand(id)`, launched by Main only after the user clicks, then `checkProvider(id)`
3. `ProviderStatus` is plain JSON and structured-clone safe, so it can cross IPC as-is.
   Render `readiness` as the badge, and show `diagnosticMessage`, `errors[].message`,
   `authentication.account/subscription` (only when non-null), and `quota` (only when not
   `UNKNOWN`).
4. The renderer must never call diagnostics per render. It reads cached status and
   refreshes on explicit user action.

## 11. Future provider extension model

`ProviderId` is `'claude-code' | 'codex' | (string & {})`, so new ids need no type change.
To add a provider (e.g. Grok, Cursor, DeepSeek; none are implemented):

- **CLI-based**: write a `CliProviderSpec` (descriptor, version/auth args + `parseAuth`,
  probe args/input/`parse`, login args, cost-risk env keys) and call
  `createCliProviderAdapter(spec)`. It inherits discovery, timeouts, redaction, readiness
  derivation and the error model.
- **Anything else**: implement `ProviderAdapter` directly (see the in-memory adapter in
  `tests/providers/provider-registry.test.ts`).
- Register it with `registry.register(adapter)`, or add it to `createDefaultProviderRegistry`.

Registering a provider only makes it diagnosable. Using it for execution would be a
separate change to the Orchestrator and is out of scope here.
