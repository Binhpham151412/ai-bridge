# AI Bridge — M4.1 Session & Execution Transparency Report

## 1. Goal

Make every Claude/Codex call inspectable without guessing: was the prompt sent, to which
Claude CLI session, what exact bytes, did the CLI start, how did it end, what did it print,
which AI Bridge session/iteration it belongs to — and, on resume, whether the same Claude
session was really continued. Every claim is labelled with the evidence behind it;
anything unproven is shown as `UNKNOWN`. No architecture change: same Core/BridgeEngine,
same run host, same Claude↔Codex workflow, no new orchestrator, no database, no API,
no cloud, no Claude Desktop dependency.

Motivating case (from real use, project `bdsdanang`): a run ended with
`REPORT_INVALID / REPORT_MISSING`. Only by reading Claude's own transcript by hand could we
see that Claude had exited 0 after answering in chat instead of writing the report file.
After M4.1 that is visible in the app ("Claude CLI kết thúc bình thường (exit code 0)
nhưng không ghi file report" + Claude's final message under "View details").

## 2. Existing architecture inspected

| Piece | Finding before M4.1 |
|---|---|
| `ClaudeCodeCliAdapter` | `claude -p --output-format stream-json --verbose` with `--session-id <uuid>` (iteration 1; the uuid is generated by AI Bridge) or `--resume <id>` (later iterations). Prompt via **stdin**; report contract via `--append-system-prompt`. Verified the CLI-reported `session_id` against the requested one (`SESSION_MISMATCH`) — but only on success. |
| `CodexCliAdapter` | `codex exec --json` / `codex exec resume <thread>`; input via stdin; thread id from `thread.started`. |
| `runProcess` | stdout/stderr buffered in memory (capped 50 MB each by M3.5), returned, then **discarded**. No PID/timestamps in the result; no evidence of stdin delivery; **no `stdin` error listener** (an `EPIPE` would have been an unhandled error in the run host). |
| Orchestrator / BridgeEngine | Prompt persisted + SHA-256 verified (M3); per-iteration integrity chain (M3.5); one log line per CLI call; events `CLAUDE_STARTED` (emitted at the state transition, *before* spawn) and `CLAUDE_EXITED`. On failure only `stderr` survived — uncapped — as `errorMessage`. |
| Session history / UI (M4) | Prompt/report/response/events/state per session; no execution metadata; one "Session" id shown (the AI Bridge one). |

## 3. Claude session model

- AI Bridge **requests** a Claude CLI session id (`--session-id <uuid>` for a new session,
  `--resume <id>` to continue). The CLI **reports** the id it actually used in its
  stream-json events (`system/init`, `result`) — AI Bridge now parses it tolerantly even
  when the call fails.
- Evidence levels stored per call (`cliSessionId.evidence`): `CONFIRMED_BY_CLI` (the CLI
  printed it) · `REQUESTED_NOT_CONFIRMED` (asked for, never confirmed — e.g. the CLI died
  before its init event) · `UNKNOWN` (neither). An id is never invented.
- **Real CLI behaviour found in this sprint:** `claude --resume <non-existent id>` exits 1
  ("No conversation found with session ID: …") yet its `result` event reports a
  **brand-new** session id (a different one each time). M4.1 therefore records continuity
  separately (§11) and the session summary only trusts the id reported by a *successful*
  call.

## 4. AI Bridge session model

Unchanged: `YYYY-MM-DD_NNN`, the orchestration run owned by AI Bridge
(`.ai-bridge/sessions/<id>/`). It is now labelled "AI Bridge session" everywhere in the UI
and shown next to — never instead of — the Claude CLI session and the Codex thread.

## 5. Codex session/thread model

Codex thread ids come only from the CLI's `thread.started` event. For a new thread nothing
is requested (`requested: null`); if the CLI reports none, the record says `UNKNOWN`
(tested). On `exec resume`, continuity is checked exactly like Claude's.

## 6. Exact prompt persistence

- Unchanged and compatible: `<session>/<NNN>-claude-prompt.md` holds the exact prompt,
  written and read back with SHA-256 verification (M3).
- New: the execution record stores `input.file`, `input.sha256`, `input.bytes`, computed
  from the same string that is written to Claude's stdin (UTF-8).
- **What "sent" means here (honest wording):** `runProcess` now observes the end of the
  stdin write (the stream's own `finish`): every prompt byte was accepted by the OS pipe
  and stdin was closed. This is recorded as `STDIN_FLUSHED_AND_CLOSED` with a timestamp and
  shown as **"PROMPT WRITTEN TO CLAUDE STDIN"** with the note "không chứng minh CLI đã
  đọc/xử lý". The real Claude CLI does not echo its input, so *receipt by Claude* is not
  claimed. (In tests the fake CLI does echo stdin, and the echoed bytes' SHA-256 equals the
  persisted prompt's — tested.) A stdin error (e.g. EPIPE) is recorded as `STDIN_ERROR`.
- The UI distinguishes, in order: PROMPT PERSISTED (file hash matches the record) →
  CLAUDE PROCESS STARTED (pid) → PROMPT WRITTEN TO CLAUDE STDIN → CLAUDE CLI SESSION
  CONFIRMED → CLAUDE COMPLETED / FAILED / TIMEOUT / RUNNING / INTERRUPTED / STOPPED.

## 7. Execution metadata

One record per CLI call, in the existing session folder (no database):
`<NNN>-claude-execution.json`, `<NNN>-codex-execution.json`
(`src/core/execution/execution-record.ts`). Written before spawn (`status: RUNNING`),
updated at spawn (pid, start time) and at stdin flush, finalized at exit.

```json
{
  "schema": 1, "agent": "claude", "iteration": 1, "bridgeSessionId": "2026-09-26_001",
  "mode": "NEW",
  "cliSessionId": { "requested": "f4f33f93-…", "reported": "f4f33f93-…", "evidence": "CONFIRMED_BY_CLI" },
  "continuity": { "expected": null, "reported": null, "verdict": "NOT_APPLICABLE", "note": "…" },
  "input": { "file": "001-claude-prompt.md", "sha256": "f8b4bef6…", "bytes": 61,
             "delivery": "STDIN_FLUSHED_AND_CLOSED", "deliveredAt": "…", "deliveryError": null },
  "process": { "pid": 3636, "startedAt": "…", "endedAt": "…", "durationMs": 28627,
               "exitCode": 0, "signal": null, "timedOut": false },
  "status": "COMPLETED", "errorCode": null,
  "output": { "kind": "CLI_OUTPUT", "stdoutFile": "001-claude-stdout.jsonl", "stderrFile": "001-claude-stderr.log", "…": "…" },
  "command": { "executable": "claude.exe", "args": ["-p", "--output-format", "stream-json", "--verbose",
               "--session-id", "f4f33f93-…", "--append-system-prompt", "<641 bytes omitted>",
               "--permission-mode", "acceptEdits"] }
}
```

The command metadata never contains the prompt (it goes through stdin) or credentials;
long arguments are summarized. A record still `RUNNING` whose session is no longer running
is displayed as `INTERRUPTED` (or `STOPPED`), never as running.

## 8. stdout / stderr / transcript handling

- Each call's stdout and stderr are persisted as `<NNN>-<agent>-stdout.jsonl` /
  `<NNN>-<agent>-stderr.log`, with credential-shaped substrings masked.
- Named **"CLI output"** everywhere: Claude's stdout is its stream-json *event output*,
  not a conversation transcript; nothing is presented as a transcript.
- Bounded: output is still capped at 50 MB per stream in memory by `runProcess` (M3.5,
  unchanged); the persisted files derive from that bounded buffer. The UI reads only the
  **last 256 KB** (`getExecutionOutput`, read from disk by byte range — no full read of a
  large file) and only when the user asks ("VIEW CLI OUTPUT" / "VIEW STDERR"). Nothing is
  streamed over IPC per output chunk.
- Output is persisted when the process ends. If the run host itself is killed mid-call,
  that call's output is lost (the record then shows INTERRUPTED/STOPPED) — see §16.

## 9. UI changes

- Dashboard: "AI Bridge session" label; the Agents card shows **Claude CLI session** and
  **Codex thread** separately, with the note that these ids come from the CLIs, not from
  Claude Desktop's conversation list.
- Artifact viewer: new **CLAUDE EXECUTION** and **CODEX EXECUTION** tabs (fields,
  evidence-based lifecycle checklist, continuity line, `VIEW EXACT PROMPT` /
  `VIEW CLI OUTPUT` / `VIEW STDERR`). Existing tabs unchanged.
- Sessions: rows show the Claude CLI session; opening a session shows a header (AI Bridge
  session, Claude CLI session, Codex thread, started, ended, final status) and a **trace
  table** — one row per iteration: Claude session, Claude status, exit code, report status
  (VERIFIED/UNVERIFIED/MISSING/OVERWRITTEN), Codex status, Codex result
  (CONTINUE/DONE/NEED_HUMAN), prompt SHA-256. Clicking a row opens that iteration's Claude
  execution. A resume mismatch is written out in the row.
- Activity log: new lifecycle rows — "Claude prompt persisted", "Claude step started",
  "Claude CLI started" (pid, session), "Prompt written to Claude stdin", "Claude CLI
  exited" (exit code, duration), "Claude session resumed" (continuity verdict; warning
  unless VERIFIED), "Claude CLI failed" (error), and the Codex equivalents. The old
  over-claiming labels "Claude completed"/"Codex response received" were renamed to
  "Claude CLI exited"/"Codex CLI exited".

## 10. Error handling

Concise codes are kept (`CLAUDE_RUN_FAILED:NON_ZERO_EXIT`, `REPORT_INVALID`, …). Core now
returns `diagnostics` with the run outcome (redacted, capped): bridge session, iteration,
CLI session id + evidence (+ requested id and continuity), status, exit code, duration,
prompt SHA-256/bytes, stdin delivery, execution record name, Claude's final message,
stderr tail (4 000 chars), stdout tail (2 000). "View details" renders all of it; the
headline message now states the exit code ("Claude CLI kết thúc với exit code 1."). For
`REPORT_INVALID` with a missing report after a clean exit the message says so explicitly
and the details include Claude's final message. `errorMessage` is now a capped, redacted
stderr tail instead of the full, unbounded stderr.

## 11. Resume behaviour

- Every call made with `--resume` records `continuity`: `VERIFIED` only when the CLI
  reported exactly the requested id; `MISMATCH` when it reported a different one;
  `UNKNOWN` when it reported none. The event "Claude CLI session … resumed — continuity
  VERIFIED/UNKNOWN/MISMATCH" is emitted after the call.
- Existing SHA-256 prompt integrity is unchanged; the trace additionally lets the user
  compare iteration N+1's prompt SHA with iteration N's extracted PROMPT (tested equal).
- Normal multi-iteration runs: continuity VERIFIED on every resumed iteration (tested with
  fake CLIs). For the real CLI, the M4 real multi-iteration runs already passed the
  adapter's unchanged requested-vs-reported session check on resume; the M4.1 real run
  reached DONE in one iteration, so a real VERIFIED record was not produced in this sprint
  (the real MISMATCH path was).

## 12. Security

All M4 guarantees unchanged (contextIsolation, nodeIntegration off, sandbox, typed IPC
allowlist, sender check, CSP, no Node in the renderer — static tests + real smoke 10/10 on
the packaged exe). One new IPC channel, `bridge:getExecutionOutput`
`{ runId: YYYY-MM-DD_NNN, iteration: 1–999, agent: claude|codex, stream: stdout|stderr }` —
validated in Main and again in Core; the file is chosen by fixed name, never by a path from
the renderer. Redaction (`core/security/redact.ts`) was extended with JSON credential keys
(`"accessToken"`, `"refresh_token"`, `"api_key"`, `"password"`, …) and
`Cookie`/`Set-Cookie`/`Authorization`/`Proxy-Authorization` headers; it is applied when
persisting CLI output, in diagnostics, in events, and again in Main before IPC. Prompts,
reports and responses remain byte-exact (not redacted), as in M4.

## 13. Performance

No unbounded buffers: `runProcess` caps unchanged; output is read back as a 256 KB tail by
byte range; diagnostics tails are capped; nothing is streamed per chunk; the activity list
is still bounded (500, memoized rows). Execution records are small JSON files written 3–4
times per call through `AtomicJsonWriter`. Full suite time unchanged (~25 s).

## 16. Known limitations

- **VERIFIED vs UNKNOWN, explicitly:** prompt bytes accepted by Claude's stdin pipe —
  VERIFIED (pipe level). Claude *having read/processed* the prompt — **UNKNOWN** (the real
  CLI does not echo input; a successful `result` event is indirect evidence only). Session
  id — VERIFIED when the CLI reports it; otherwise shown as requested/UNKNOWN. Resume
  continuity — VERIFIED/MISMATCH/UNKNOWN per call.
- Output files are written when the CLI process ends; a run-host kill mid-call loses that
  call's output (the record remains, as INTERRUPTED/STOPPED).
- The real Claude CLI's stream-json stdout is event output, not a full transcript. Claude
  keeps its own transcript under `~/.claude/projects/…`, which AI Bridge deliberately does
  not read (undocumented format, user-private data).
- Sessions recorded before M4.1 have no execution records; the UI says so.
- Codex has no "final message" field in diagnostics (its response file is already shown).
- The packaged exe in `release/` was open during this sprint, so the new build was
  packaged to `release-m4.1/` (`package-win.ts --out`); the running app was not touched.
- The report-contract behaviour seen in `bdsdanang` (Claude answering in chat instead of
  writing the report) is now *visible*, not *prevented* — changing the contract or
  workflow was out of scope for M4.1.
- Fixed during this sprint (found by the real failure test and by inspection): diagnostics
  called the id from a failed `--resume` "confirmed" (now MISMATCH with both ids); the
  session summary could adopt that id (now prefers the id from successful calls); a stdin
  `EPIPE` could crash the run host (now handled).
